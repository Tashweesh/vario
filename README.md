# VAIRO — Erbil real estate: website + CMS + CRM

React (Vite) single-page app on a Supabase backend, built from the Claude Design handoff in
[`project/VAIRO Prototype.dc.html`](project/VAIRO%20Prototype.dc.html) (see [`HANDOFF.md`](HANDOFF.md) and [`chats/`](chats/)).
Arabic, right-to-left, responsive (desktop and phone).

| App | URL | Who |
| --- | --- | --- |
| Public website | `/`, `/buy`, `/rent`, `/property/:id`, `/projects`, `/areas`, `/developers`, `/sell`, `/contact`, `/saved`, `/compare`, `/map`, `/tools/*`, `/guides`, `/invest` | everyone |
| CMS | `/cms` (listings, projects, developers, areas, homepage & site settings, users & roles) | staff |
| CRM | `/crm` (pipeline, contacts, viewings calendar, reports) | staff |
| Staff login | `/login` | staff |

## Stack

- **Frontend:** React 18, React Router 6, `@supabase/supabase-js` 2, Vite 5. Styling copies the design's inline styles 1:1, plus a small CSS file for hover states.
- **Backend:** Supabase Postgres + Auth (email/password) + Storage (public `media` bucket). All rules live in the database:
  row-level security, triggers and two RPCs. There is no custom server.
- **Maps:** Leaflet on OpenStreetMap tiles, no API key. Areas carry a centre (`lat`/`lng`, set by clicking the map in CMS → المناطق);
  listings and projects may carry their own pin (CMS editors → «الموقع على الخريطة»), otherwise they are counted in their area's pill on `/map`
  and shown at the area centre marked «موقع تقريبي». Set `VITE_MAP_TILE_URL` / `VITE_MAP_TILE_ATTR` to use another tile provider.

```
supabase/migrations/   schema, RLS, triggers, RPCs, storage bucket
supabase/seed.sql      sample data from the design (generated by scripts/gen-seed.mjs)
src/site/              public website (SiteData.jsx loads the catalog; pages/)
src/cms/  src/crm/     staff apps (each has its own data provider + pages/)
src/staff/             login, auth gate, shared sidebar shell
tests/                 API tests, browser smoke + flow tests, local test stack
```

## Run locally

Requires Node 20+ and the Supabase CLI (installed as a dev dependency) with Docker.

```bash
npm install
npx supabase start            # starts Postgres/Auth/Storage, applies migrations + seed
cp .env.example .env.local    # paste the API URL and anon key that `supabase start` printed
npm run dev                   # http://localhost:5173
```

## Deploy

1. Create a Supabase project, then `npx supabase link --project-ref <ref>` and `npx supabase db push` (applies the migrations; the seed is **not** pushed).
2. Bootstrap the first admin in the SQL editor:
   ```sql
   insert into agents (id, name, title) values ('owner', 'اسمك', 'مدير');
   insert into staff (agent_id, email, role) values ('owner', 'you@company.com', 'admin');
   ```
   Then open `/login` → «أول مرة؟ فعّل حسابك» with that email. Everyone else is invited from **CMS → المستخدمون والصلاحيات**.
3. In Supabase **Authentication → URL configuration**, set the site URL and add `https://<your-domain>/login` as a redirect URL (used by password reset).
4. Build with `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` set, and host `dist/` on any static host. SPA fallbacks are included for Netlify (`public/_redirects`) and Vercel (`vercel.json`).

### Docker

`Dockerfile` builds the site and serves `dist/` with nginx on port 80 (SPA fallback included). `docker-compose.yml`
names the container `vario`, joins the external `npm_default` network (Nginx Proxy Manager) and publishes port 80 on a
random host port. Point an NPM proxy host at `http://vario:80`.

```sh
cp .env.example .env            # VITE_* values are baked in at build time
docker compose up -d --build
```

### CI/CD (GitHub Actions)

`.github/workflows/deploy.yml` runs on every push to `main`: it SSHes into the server, clones/updates the repo at
`DEPLOY_PATH`, writes `.env` from secrets and runs `docker compose build && docker compose up -d`.

Repository **secrets**: `SSH_HOST`, `SSH_USER`, `SSH_KEY` (private key), `SSH_PORT` (optional, default 22),
`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, and `REPO_TOKEN` (a fine-grained PAT with read access, only needed
while the repo is private). Repository **variables** (optional): `DEPLOY_PATH` (default `~/vario` of the SSH user),
`VITE_MAP_TILE_URL`, `VITE_MAP_TILE_ATTR`. The server needs `git` and Docker with the compose plugin, and the SSH
user must be in the `docker` group.

## Roles and data rules (enforced in Postgres)

| | Visitor | Agent (وسيط) | Editor (محرر محتوى) | Admin (مدير النظام) |
| --- | --- | --- | --- | --- |
| Read published listings, projects, areas, developers | ✓ | ✓ | ✓ | ✓ |
| Draft listings, owner info, change log | – | ✓ (owner info: own listings) | ✓ | ✓ |
| Create/edit listings | – | own listings, **drafts only**; cannot publish, feature or reassign | ✓ publish, feature, delete | ✓ |
| Photos & floor plans (storage) | – | own listings | ✓ | ✓ |
| Projects, developers, areas, tower unit grid | – | – | ✓ | ✓ |
| Homepage, site settings, featured order, users & roles | – | – | – | ✓ |
| CRM (contacts, activities, viewings) | – | ✓ | ✓ | ✓ |

- Public forms never touch tables directly: they call `submit_lead(...)`, which validates input, de-duplicates by phone,
  links only public listings, auto-assigns the listing's agent, logs a «طلب من الموقع» activity and bumps the listing's lead count.
- `track_listing_view(id)` counts property page views (once per browser session).
- Deactivating a team member removes all their database access immediately; the last active admin cannot be demoted or removed.
- **«إظهار الوسيط المسؤول»** (CMS → الرئيسية وإعدادات الموقع) hides agent profiles at the database level; property pages then show «فريق ڤايرو» and the office number.
- Listing IDs are generated automatically (`VS-…` for sale, `VR-…` for rent).

## Tests

```bash
npm run test:api          # 30 API tests through supabase-js, as visitor/agent/editor/admin/un-invited user
node tests/ui-smoke.mjs   # opens every route on desktop + phone, as visitor and staff; fails on errors/overflow
node tests/ui-flows.mjs   # browser flows: book a viewing → appears in CRM; create+upload+publish a listing;
                          # hide agent site-wide; drag a lead in the pipeline, add a note, schedule a viewing
```

The tests write data: run them against a freshly seeded **local** database (`npx supabase db reset`). The API test refuses
non-local URLs unless `ALLOW_REMOTE=1`. Browser tests need `npm run dev` running and accept `BASE` and `CHROMIUM_PATH`.

`tests/stack/` is a fallback for machines without Docker: it runs the same migrations on a plain Postgres 16 with a small
Supabase shim (`shim.sql`), PostgREST, and a gateway (`gateway.mjs`) that serves the `/rest`, `/auth` and `/storage` HTTP routes
supabase-js uses. See `reset-db.sh` and `start.sh`. The official `supabase start` stack is the reference environment.
